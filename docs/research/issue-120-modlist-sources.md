# Download and redistribution rules for modlist sources

Checked 2026-09-28. Research for [Verify download and redistribution rules for modlist sources](https://github.com/Reilley64/mods/issues/120), part of [Map modlist publishing and installation](https://github.com/Reilley64/mods/issues/119).

This note records host rules and available mechanisms. It does not select a first-release architecture or grant permission for any particular mod.

## Findings

| Source | Supported acquisition mechanism | User action and limits | Redistribution |
| --- | --- | --- | --- |
| Nexus, free account | User downloads on the website and supplies the archive. A registered manager can use a website-generated `nxm` download key. | Account authorization does not remove the per-file website action. The API download-key exception requires the key and its expiry. | Download access does not grant rehosting rights. Check each file's permissions. |
| Nexus, Premium account | A registered application can request file download URLs through the authenticated API without the free-account website key. | User authorizes the application. API quotas and other host restrictions still apply. | Premium changes acquisition, not the mod's license. |
| GitHub release | Download the author's public release asset through its `browser_download_url` or the release-asset REST endpoint. | Public assets need no token. Private assets require authorized access. REST quotas and secondary limits apply. | Check the asset's license, including bundled dependencies. Public visibility is not a redistribution license. |
| Local archive | User supplies a lawfully obtained archive, or an author supplies an archive they have permission to share. | No host request is necessary to read an existing local file. Its original license still applies. | Possession, local import, and a checksum do not establish permission to upload it to our repository. |

These conclusions follow from the API documentation and rights policies below. The local-file conclusion is an inference about local processing, not a new host permission.

## Nexus authorization and API access

The [API Acceptable Use Policy][nexus-aup] allows personal API keys for personal use and testing. A public-facing application must contact `support@nexusmods.com` with a testing build and complete registration before wider end-user use. Registration supplies an application slug. Users can revoke application keys. SSO is available after registration but is not mandatory.

The [official API client's authorization documentation][nexus-client] describes the user approving the application in their browser and receiving an application-specific API key. It explicitly rejects using a key created for another application. Requests must identify the application and version. A Premium subscription is neither application registration nor user authorization.

The [official client's download method][nexus-download] says a non-Premium user needs a key generated by the website's "Download with Manager" button. Its request includes `key` and `expires` when supplied. This download key is distinct from the account API key. The documented Premium path does not need that per-file key. Free accounts therefore have API access, but an API key alone does not entitle them to unattended downloads.

Supported paths include ordinary website downloads followed by local archive import, and the registered manager download API under the account's entitlements. The documentation establishes a user-mediated `nxm` path for free accounts. It does not authorize a new application to automate website clicks, scrape download pages, replay another user's links, or impersonate Wabbajack or Vortex.

The AUP lists these unacceptable uses:

- Bulk fetching data to rehost it on another service.
- Storing users' API keys on our server or using them without user-initiated action.
- Personal API keys in a public-facing application outside the testing exception.
- Blank or impersonated application identity metadata.

The [Terms of Service][nexus-terms], sections 10, 11, and 24, restrict site use, prohibit scraping and automated site extraction, and distinguish downloading for recreation from distribution permitted by the uploader. Use the documented API within its AUP. Do not treat browser automation as an alternative to registration or Premium restrictions. The terms also make third-party API users responsible for filtering returned age-restricted content. The exact obligations for this installer need confirmation with Nexus.

## Nexus rate limits

The [current rate-limit help article][nexus-rates], updated June 3, 2026, states **20,000 requests per 24-hour period, then 500 requests per hour**. Once both allowances are exhausted, callers must wait. It says the daily quota resets at 00:00 GMT and the hourly quota at each hour. Response headers report the remaining allowance and reset times. Metadata and update checks also consume requests. The article does not give free and Premium users different server quotas.

The [official client README][nexus-client] separately describes client-side burst quotas of 300 requests, or 600 for Premium, replenished at one request per second, plus server HTTP 429 responses. These are library throttles, not substitutes for the current server limits. Older 2,500-per-day guidance should not be copied into the spec. No authenticated quota or download test was performed, so implementation must honor live response headers and backoff signals rather than assuming these published numbers cannot change.

## What Wabbajack establishes

The [Viva New Vegas maintainer's installation guide][vnv] tells users to accept the Nexus API request and says, "If you are not a Premium user you will need to manually click download for each mod." This is first-party evidence for that list's documented Wabbajack workflow. Wabbajack's own [installation documentation][wabbajack] also tells users to acquire third-party or external files before installation and describes its downloaded-archive directory.

This demonstrates that a modlist installer can require manual acquisition and then install from archives. It does not establish that Wabbajack's application registration, access to archived files, CDN permissions, or other agreements transfer to this project. Its integration is not a license to automate free-account download clicks. This research did not test Wabbajack or audit its current downloader implementation.

## GitHub release downloads

GitHub's [release-asset REST documentation][github-assets] explicitly supports fetching `browser_download_url` or requesting the API asset with `Accept: application/octet-stream`. API clients must handle either a 200 stream or a 302 redirect. Public resources work without authentication. For private resources, a fine-grained token needs repository `Contents` read permission and access to that repository. A public release download does not impose Nexus-style Premium membership or per-file website confirmation.

GitHub's [REST rate-limit documentation][github-rates] gives unauthenticated requests a limit of 60 per hour per originating IP. Typical authenticated user requests share a 5,000-per-hour user allowance. Some application and enterprise cases differ. Secondary limits also apply, including concurrency and request-point limits. Follow response headers and retry instructions. These figures concern REST API calls, not a promise that direct asset downloads have unlimited bandwidth or availability.

Author-hosted release assets are an available acquisition source. Republishing them is a separate question. GitHub's [licensing guide][github-license] says that without a license, default copyright restrictions apply. The right to view and fork a public repository does not confer a general right to redistribute its release binaries elsewhere. Inspect licenses that apply to the actual binary and bundled assets, not just the repository's visibility or license badge.

## Local archives, configurations, and patches

Nexus's [File Submission Guidelines][nexus-files] state that credit does not replace explicit permission, permissions are file-specific, and absent permission information means asking the author. Its terms grant Nexus and its partners rights that should not be assumed to apply to an independent repository. An uploader must also hold the rights to third-party content they include.

Apply that distinction to each proposed artifact:

- A recipe that references a mod is different from hosting the mod's bytes. Nexus's [Collections guidelines][nexus-collections] explicitly distinguish references from redistribution. Those guidelines govern Nexus Collections; they do not put independently hosted recipes in the public domain.
- An author's original configuration may be distributed under that author's applicable permission. A configuration copied from another list or containing third-party material needs its own rights check. The filename or extension does not settle ownership.
- A patch or tool-generated file is not automatically exempt. Determine whether it contains someone else's assets and whether the relevant licenses allow modification and distribution. A binary delta is not proof of permission. Local generation avoids hosting the complete output but is not a blanket exception to modification restrictions.
- Nexus Collections' bundled-assets rules permit specific tool outputs under their guidelines, disallow bundling mods, and direct standalone patches to their own mod pages. This is not blanket authorization to bundle those files in our repository.
- Importing a user's existing archive does not itself upload or rehost it. If a list author gives that archive to other users, the author is distributing it and needs permission for all included content. Keep that separate from the user's own local installation.

These are rights checks, not a legal determination for any specific file. No candidate archive, configuration, or patch was submitted for a license audit.

## Questions for hosts and authors before relying on an integration

Contact Nexus support with the proposed client and intended API usage to confirm registration, user authorization, the free-account `nxm` flow, and any embedded-browser behavior. Ask how to meet age-restricted-content requirements. Confirm whether the project can resolve archived versions and what to do when a pinned file is hidden, removed, unavailable, or no longer accessible to that user. The research does not establish an entitlement to archived files or permanent download URLs.

Ask Nexus before proposing server-side metadata synchronization or caching beyond normal client use. Bulk rehosting and server custody of user API keys conflict with the published AUP. Clarify any needed exception rather than inferring it from another manager's behavior.

For a normal public GitHub release asset, the download documentation does not identify a separate registration requirement. Private releases need repository-owner access. Large-scale mirroring or unusual traffic needs a separate host-policy review; the REST download endpoint is not a redistribution agreement.

Ask each rights holder when the license is absent, ambiguous, limited to Nexus, or does not clearly cover off-site redistribution and modification. Keep written evidence for the exact files and versions. Do not interpret silence or a local archive as consent.

## Evidence and limits

All linked sources were retrieved on 2026-09-28 over public HTTP. Nexus's main-site terms URL returned an anti-bot page; the official help-site terms were accessible. The Nexus API root required authentication. No account keys, private APIs, downloads, or user accounts were exercised. Policy facts are current published guidance, not an approval of this application. Host-contact items above are explicit limits on supported claims, not unanswered claims of permission.
