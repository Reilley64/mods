# Export resolved files and Profile State

Use `mods [--environment PATH] export OUTPUT [--include-saves] [--include-game-data] [--dry-run]` to create a folder of resolved ordinary files. `OUTPUT` is relative to the shell's startup working directory, not the Environment Root. The destination parent must exist; `OUTPUT` must not exist, even if empty. Choose a destination outside the Environment Root. Run `--dry-run` to inspect paths, providers, file counts and bytes without creating or reserving output; with `--include-game-data`, game files are listed with provider kind `steam_data`. Rerun without it only after checking the destination and stopping programs that write the source. Export prepares the environment the same way as `exec`: it creates a missing `meta.toml` for enabled mods, and it stages the derived profile INIs in the Environment Root's `temp` folder and removes them again, also for `--dry-run`. Normal success prints nothing on stdout. On stderr, export prints the same plugin warnings as `exec`.

```powershell
mods --json --environment 'D:\Mod Environments\Mojave' export 'D:\Exports\Mojave' --dry-run
# After reviewing the preview and approving the write:
mods --json --environment 'D:\Mod Environments\Mojave' export 'D:\Exports\Mojave'
```

With `--json`, stdout is one document: `outcome` (`preview` or `published`), `output`, `total_bytes`, `files` (each with `path`, `bytes`, and `provider`), and `warnings` (`stale_plugin_entry` or `duplicate_plugin_entry` with `details.plugin`). A failure is a Problem on stderr; its `details` can include `output`, `retained_partial_output`, `retained_export_stage`, `output_complete`, and `load_order_file`. See [JSON output](https://github.com/Reilley64/mods/blob/main/docs/cli/json.md).

The package has separate `Data/` and `profile/` directories. **Place files manually** at a compatible destination only after checking its game version, file conflicts and existing profile. Copy `Data/` contents beneath the destination game's `Data/`, not as a second nested `Data/`. Do not copy `profile/` wholesale into `Data/` or assume it maps to one runtime directory. Place game INIs (such as `Fallout.ini`, `FalloutPrefs.ini`, `FalloutCustom.ini`, `GECKCustom.ini`, and `GECKPrefs.ini`) in the destination's corresponding Documents/My Games profile, and `plugins.txt` and `Plugins.fnvviewsettings` in its corresponding Local AppData game profile. `plugins.txt` lists the active plugins. Its line order is the load order. To change the load order, reorder its lines. Export does not write a `loadorder.txt`. With `--include-saves`, place `profile/saves/` in the intended Documents/My Games save location after checking for existing saves. The exact paths depend on the destination's Windows or Proton prefix configuration; identify them first. `modlist.txt` records provenance and is not game activation state. Missing optional source files stay missing; the package does not fill them in. The exported `Fallout.ini` routes saves to `Saves\`. Its `sArchiveList` puts `Fallout - Invalidation.bsa` first, followed by the list from `FalloutCustom.ini` or `Fallout.ini`. When neither file sets `sArchiveList`, export uses the built-in English Steam default list; it does not read the game's `Fallout_default.ini`.

Only enabled analytical Data winners, unique participating files and effective Overwrite files are selected. By default, the game's own Data files (Steam-base files) are not exported. With `--include-game-data`, export also copies every winning file from the Game Installation's `Data` folder: base game and DLC plugins and BSAs, and loose files such as `Music`, `Sound`, `Video`, `Shaders`, and `NVSE`. Files that a Data Mod or Overwrite overrides are exported from the winning provider, so the output `Data/` is a complete Data folder. Game root files, such as executables, the xNVSE loader, and DLLs, are never exported. Disabled or losing providers and manager-private metadata are not exported. Ordinary mod-supplied plugins and INIs remain Data files. BSA files are opaque: export copies physical BSA bytes but does not inspect their members. The support `Data/Fallout - Invalidation.bsa` is an explicit generated exception, not a mod winner or bundled base asset. It also replaces a `Fallout - Invalidation.bsa` in the game's `Data` folder when `--include-game-data` is used. Exported INIs carry the matching invalidation settings; placing the BSA alone is insufficient. Check those INIs and the destination's own archive setup before launching. Export does not prove in-game invalidation.

Each copy keeps the modification time that the platform copy gives it: the source time on Windows, and usually the copy time on other systems. After it writes the files, export sets the times of the plugins and BSAs in the output `Data/` root in load order, with the same rules as [`exec`](execution.md#load-order-through-file-times). Without `--include-game-data`, the game's own Data files are not in the output, so the destination's own base game and DLC plugins keep their dates. The exported mod plugins are timed from 2000-01-01, so at a destination they can sort **before** the Steam-dated DLC masters they need. **Use `--include-game-data` when the output is meant as a full game setup.** With it, the base game and DLC plugins and BSAs in the output also get their load-order times. Read-only source files stay read-only in the output. Export does not preserve ACLs, creation times or alternate streams. `plugins.txt` is copied as state, not recomputed. Export does not rewrite mod paths, install a mod manager, synchronize saves or change the destination automatically. Upstream usvfs mappings are not guaranteed to implement analytical Tombstone suppression at runtime; this export follows the analytical positive-file resolution rather than a capture of every runtime-visible file. A copied folder is not a guaranteed playable setup.

Source writers must be stopped before preview and export. Preview reserves nothing and does not ensure the later export sees identical sources. Export does not compare sources again while it copies, so a change made during export can appear in the output. Export creates the new destination folder and writes files into it directly. Failures or cancellation can leave partial files in the destination; stderr reports that folder as `retained_partial_output`. This includes a failure to set the load-order times after all files were written; stderr then also reports `phase = load_order`. Inspect it before any manual cleanup or retry. Export does not roll back or delete partial state. If export cannot remove its INI stage from `temp`, stderr reports it as `retained_export_stage`, and the exit status is 1. When that happens after a complete write, stderr also says that the export output is complete and only the temp stage remains. The stage holds only derived copies; delete it before the next `exec` or `export`, which refuse a non-empty `temp`. No destination apply or game launch occurs.
